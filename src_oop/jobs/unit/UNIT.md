# Модуль `src_oop/jobs/unit`

Этот модуль обслуживает листы UNIT и связанные с ними служебные обновления.

Если говорить простым языком, здесь собрана логика, которая помогает держать управленческую таблицу UNIT в актуальном состоянии: подтягивать в неё важные признаки по товарам и статусы, чтобы по одной таблице можно было быстро смотреть состояние ассортимента и принимать решения.

## Что именно делает модуль

Внутри модуля сейчас живут несколько отдельных сценариев:

### 1. Работа с основным листом UNIT

Файл `unit.py` даёт базовую точку входа для работы с таблицей UNIT:

- подключается к базе данных проекта;
- подключается к основному или тестовому листу Google Sheets;
- умеет читать лист UNIT в `DataFrame`;
- умеет получать данные по рекламным расходам.


### 2. Обновление признака участия в рекламе

Файл `update_adv_participants.py` отвечает за простой бизнес-сценарий:

- берёт из базы данные о статьях, по которым вчера были рекламные расходы;
- открывает лист UNIT;
- для каждой строки проверяет артикул;
- проставляет в колонке `Реклама`, был ли этот товар участником рекламы.

Задача этого сценария не в расчётах, а в быстрой маркировке товаров: был ли у артикула факт рекламного расхода за вчера.

### 3. Обновление статуса товара по `wild`

Файл `update_wild_statuses.py` нужен для синхронизации статусов товара:

- читает отдельный справочник со статусами;
- берёт из UNIT колонку `wild`;
- сопоставляет строки по `wild`;
- переносит найденный статус в колонку `Статус товара`.

Здесь важна бизнес-осторожность: перед записью сценарий проверяет, что после сопоставления количество строк не изменилось. Это защита от ситуации, когда из-за дублей или грязных данных обновление случайно “размножит” строки и испортит лист.

## Откуда модуль берёт данные

В зависимости от сценария используются разные источники:

- Google Sheets с листами UNIT;
- основная база проекта;
- отдельные вспомогательные Google-листы со статусами.

То есть модуль не хранит бизнес-данные сам, а выступает как слой синхронизации между источниками и рабочей таблицей UNIT.

## Какие бизнес-правила здесь важны

У модуля есть несколько важных правил, которые повторяются в разных сценариях:

- нельзя менять порядок строк в UNIT;
- нельзя записывать данные “по ощущению”, если после сопоставления изменилась длина таблицы;
- перед записью нужно убедиться, что нужные колонки реально существуют;
- пустые значения, пробелы и дубли нужно нормализовать до записи;
- тестовый и основной лист UNIT должны поддерживаться отдельно через конфиг.

Иначе говоря, главная цель модуля не просто “что-то записать в таблицу”, а аккуратно обновить UNIT без риска тихо испортить рабочие данные.

## Зачем это нужно бизнесу

В терминах бизнеса модуль помогает ответить на несколько прикладных вопросов:

- какие товары участвовали в рекламе;
- какой статус сейчас у товара;

Это делает лист UNIT удобной точкой ежедневного контроля: команда может смотреть не в несколько разрозненных источников, а в одну таблицу, где уже собраны ключевые признаки для работы с ассортиментом и рекламой.

## Что важно понимать про границы модуля

Этот модуль не является самостоятельной системой аналитики и не принимает решения за пользователя.

Он решает более узкую задачу:

- забрать данные из источников;
- проверить, что они безопасны для обновления;
- записать результат в понятные рабочие колонки листа UNIT.

Поэтому правильнее воспринимать `src_oop/jobs/unit` как набор обслуживающих джоб для операционного листа UNIT, а не как отдельный бизнес-сервис.
