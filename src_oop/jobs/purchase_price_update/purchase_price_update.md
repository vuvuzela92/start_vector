# Purchase Price Update

## Назначение

Модуль `purchase_price_update` автоматически обновляет закупочную цену в листе
`Сопост` таблицы `UNIT 2.0 (tested)` по актуальным данным из PostgreSQL и
пишет историю изменений в лист `UNIT: Изменение закупочной цены`.

Функционал нужен для того, чтобы:

- поддерживать закупочную цену в `Сопост` в актуальном состоянии;
- учитывать не только новые поставки, но и корректировки старых документов;
- не менять строки, которые в UNIT явно заблокированы для автоперезаписи;
- сохранять понятную историю того, какие цены и когда были изменены.

## Точка входа

Боевая задача зарегистрирована в `src_oop/tasks_registry.py` под именем:

- `purchase_price_update_run`

Основная точка входа в коде:

- `src_oop/jobs/purchase_price_update/run.py -> purchase_price_update_run`

Диагностический режим без записи в Google Sheets:

- `src_oop/jobs/purchase_price_update/run.py -> purchase_price_update_compare`

## Источники данных

### PostgreSQL

Источник новых закупочных цен — таблица `supply_to_sellers_warehouse`.

Из неё берутся:

- бизнес-ключ `local_vendor_code`;
- документ поставки;
- сумма и количество;
- валюта;
- `planned_cost`;
- время последней корректировки `update_document_datetime`.

### Google Sheets

Используются два листа:

1. `UNIT 2.0 (tested) -> Сопост`
   Это рабочий лист, где хранится текущая закупочная цена по `wild`.

2. `Новый товар -> UNIT: Изменение закупочной цены`
   Это лист истории, куда добавляются строки по факту найденных изменений.

## Бизнес-логика

### 1. Как выбирается кандидат на новую цену

По каждому `local_vendor_code` модуль берёт одну самую актуальную запись из БД.
Актуальность определяется по `update_document_datetime`, а не по дате поставки.

Это важно, потому что цена может измениться:

- из-за новой поставки;
- из-за исправления уже существующего документа задним числом.

Именно поэтому модуль ориентируется на последнее изменение документа, а не
только на факт прихода товара.

### 2. Какие строки из БД вообще участвуют в расчёте

В выборку попадают только записи, которые одновременно:

- `is_valid = TRUE`;
- имеют `local_vendor_code`, начинающийся с `wild`;
- не относятся к поставщику `РВБ ООО`;
- имеют `quantity != 0`;
- попадают в окно выборки по `update_document_datetime`.

Окно построено по календарным дням и включает текущий день целиком.
Это сделано специально, чтобы дневные корректировки документа не терялись при
запуске задачи в тот же день.

### 3. Откуда берётся новая закупочная цена

По умолчанию новая цена считается как:

- `ROUND(amount_with_vat / quantity, 2)`

Но есть особые случаи, когда вместо этой фактической цены нужно брать
`planned_cost`.

Сейчас модуль использует `planned_cost`, если выполняется хотя бы одно условие:

- валюта не равна `643`;
- имя поставщика содержит `ZILOL`.

Для этого в SQL введён отдельный флаг `use_planned_cost`, чтобы одно и то же
правило одинаково применялось:

- и для расчёта `price_per_item`;
- и для постановки `alarm_flag`.

### 4. Когда выставляется тревога по цене

Если модуль решил использовать `planned_cost`, но:

- `planned_cost IS NULL`, или
- `planned_cost = 0`,

то в данных БД формируется служебный флаг:

- `ALARM: planned_cost missing`

Это не блокирует саму загрузку данных из БД, но позволяет увидеть проблему в
диагностике и понять, почему для части SKU цена может быть неполной или
сомнительной.

### 5. Как происходит сопоставление с UNIT

Сопоставление с листом `Сопост` выполняется по бизнес-ключу:

- `local_vendor_code` из БД;
- `wild` из Google Sheets.

Модуль не опирается на визуальный порядок строк в листе.

Это защищает сценарий от ручных перестановок строк в `Сопост`, потому что
товар ищется по артикулу, а не по позиции в таблице.

### 6. Какие строки запрещено менять

Если в листе `Сопост` для строки стоит признак:

- `Неизменяемая цена = 1`

то такая строка исключается из обновления даже в том случае, если в БД уже
появилась другая цена.

Это отдельное ручное бизнес-правило, которое выше автоматического расчёта.

### 7. Какие строки попадают в обновление

После нормализации и merge модуль оставляет только строки, которые:

- присутствуют и в БД, и в `Сопост`;
- не заблокированы флагом `Неизменяемая цена`;
- имеют корректно вычисленную новую цену;
- действительно отличаются от текущей цены в `Сопост`.

Если цена уже совпадает, строка не обновляется и в историю не попадает.

### 8. Что считается “реальным изменением”

Изменением считается ситуация, когда:

- `price_per_item != unit_price`

То есть модуль не реагирует на сам факт наличия новой записи в БД.
Он реагирует только на итоговую разницу между:

- новой расчётной ценой из БД;
- текущей ценой, уже записанной в `Сопост`.

### 9. Как считается разница

В рабочей подготовке разница в рублях считается как:

- `unit_price - price_per_item`

Разница в процентах считается относительно текущей цены в UNIT.

Если прежняя цена в отчётном слое отсутствует, для истории она подставляется
как `0`, чтобы поле разницы не оставалось пустым.

### 10. Что считается подозрительным изменением

Если модуль видит отклонение по цене не меньше порога:

- `25%`

строка попадает в блок `suspicious_rows`, а в лог пишется предупреждение.

Это не останавливает обновление, но помогает быстро заметить аномальные
скачки цены.

## Технический сценарий по шагам

1. `repository.py` читает данные из PostgreSQL.
2. `service.py` читает лист `Сопост` из Google Sheets.
3. `processor.py`:
   - валидирует обязательные колонки;
   - нормализует цены и ключи;
   - убирает пустые `wild`;
   - исключает заблокированные строки;
   - сопоставляет БД с UNIT;
   - выделяет только реально изменившиеся строки.
4. `service.py` ещё раз сверяет `wild` перед записью в целевую строку.
5. Модуль пакетно обновляет колонку `Стоимость в закупке (руб.)` в `Сопост`.
6. По обновлённым строкам строится отчётный DataFrame.
7. Отчёт:
   - сохраняется локально в CSV;
   - добавляется в лист `UNIT: Изменение закупочной цены`;
   - обновляет статус в ячейке `A1` листа истории.

## Защитные проверки

В модуле есть несколько защитных механизмов, которые важны для боевого запуска.

### Проверка структуры листа

Если в `Сопост`:

- нет обязательных колонок;
- нет строки заголовков;
- дублируются заголовки;
- дублируется `wild`;

задача останавливается с ошибкой, потому что безопасное обновление невозможно.

### Проверка строки перед записью

Перед записью модуль не просто берёт номер строки, а проверяет, что в этой
строке по-прежнему стоит ожидаемый `wild`.

Это защита от ситуации, когда пользователь вручную передвинул строки между
чтением листа и записью результата.

### Retry для Google Sheets

Операции записи в Google Sheets выполняются с ограниченным retry для временных
ошибок:

- `429`
- `500`
- `502`
- `503`
- `504`

Если ошибка не относится к временным, она пробрасывается сразу.

## Что сохраняется в отчёте

Лист истории получает строки с такими полями:

- `product_name`
- `local_vendor_code`
- `guid`
- `document_number`
- `quantity`
- `unit_price`
- `price_per_item`
- `price_diff_rub`
- `update_document_datetime`
- `insert_date`

Дополнительно локальный snapshot сохраняется в:

- `logs/changed_purchase_prices.csv`

Этот файл нужен для разбора инцидентов после боевого запуска.

## Статусы и исключения

### Нормальный успешный сценарий

Если изменения найдены:

- цены обновляются в `Сопост`;
- строки добавляются в лист истории;
- в лог возвращается сводка по количеству строк.

### Сценарий “менять нечего”

Если после сопоставления не найдено ни одной строки с реально изменившейся
ценой, выбрасывается:

- `NoPurchasePriceChangesError`

Это не обязательно ошибка данных. Часто это означает одно из двух:

- в выбранном окне БД нет новых корректировок;
- цена в `Сопост` уже совпадает с актуальной ценой из БД.

### Ошибки качества данных

Используются исключения:

- `MissingRequiredColumnsError`
- `DuplicateBusinessKeyError`
- `RowAlignmentError`

Они сигнализируют не о сетевой проблеме, а о том, что сценарий нельзя
безопасно продолжать из-за состояния данных или таблицы.

## Структура модуля

- `config.py`
  Конфигурация листов, SQL-запроса, колонок, порогов и путей.

- `repository.py`
  Чтение исходных цен из PostgreSQL.

- `processor.py`
  Чистая подготовка данных, сравнение БД с UNIT и формирование отчётного набора.

- `service.py`
  Боевой orchestration: чтение, подготовка, запись, retry, статус, отчёт.

- `comparison.py`
  Диагностическое сравнение с legacy-совместимым поведением.

- `run.py`
  Публичные точки входа для боевого и compare-режима.

## На что смотреть при разборе проблем

Если результат кажется неверным, в первую очередь стоит проверить:

1. Попадает ли SKU в окно выборки по `update_document_datetime`.
2. Не стоит ли в `Сопост` признак `Неизменяемая цена = 1`.
3. Совпадает ли `wild` между БД и строкой в `Сопост`.
4. Не совпадает ли уже текущая цена в `Сопост` с новой ценой из БД.
5. Не пустой ли `planned_cost` в сценариях, где должен использоваться именно он.
6. Не попал ли SKU в `absent_in_unit_codes` или `missing_price_codes`.

## Короткое резюме

`purchase_price_update` — это сценарий точечного обновления закупочной цены в
`Сопост`, который:

- берёт последнюю актуальную версию цены из БД;
- учитывает специальные правила по валюте и поставщику `ZILOL`;
- не трогает заблокированные строки;
- обновляет только реально изменившиеся SKU;
- пишет понятную историю изменений в отдельный лист.
