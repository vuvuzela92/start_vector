# План продаж: что уже реализовано

Документ описывает текущий технический фундамент для будущего плана продаж по маркетплейсу.

На текущем этапе мы не считаем финальный план целиком, а собираем и сохраняем в PostgreSQL опорные справочники и ежедневные снимки, на которых дальше будет строиться расчет.

## Что уже сделано

Реализованы три отдельных слоя данных:

1. Исторический дневной справочник менеджеров.
2. Актуальный справочник учетной категории по `wild`.
3. Исторический дневной слой статусов `wild` для учета дней наличия.

Все три слоя загружаются отдельными задачами и могут обновляться независимо.

## 1. Дневной справочник менеджеров

### Зачем нужен

Этот слой нужен для того, чтобы в будущем можно было понимать, какой менеджер и в какой день отвечал за определенный предмет.

Текущая таблица хранит именно ежедневный снимок состояния справочника, а не только последнее значение.

### Источник

- Google Sheets: `Панель управления продажами Вектор`
- Лист: `Справочник Категория-Менеджер`

### Какие поля берем

- `Предмет`
- `Менеджер`

### Куда сохраняем

Таблица в PostgreSQL:

- `sales_plan_category_manager_reference`

### Какие поля хранятся в БД

- `snapshot_date` — дата снимка справочника
- `subject_name` — предмет
- `manager_name` — менеджер
- `loaded_at` — время загрузки строки в БД

### Бизнес-правила

- таблица хранит историю по дням;
- одна строка соответствует одной связке `предмет + менеджер` на дату снимка;
- лишние поля источника в таблицу не сохраняются.

### Задача для запуска

- `sync_sales_plan_manager_reference_to_db`

## 2. Справочник учетной категории по wild

### Зачем нужен

Этот слой нужен для обязательного бизнес-правила:

- один `wild` должен входить только в одну учетную категорию;
- дублирование одного и того же `wild` по нескольким категориям в плане недопустимо.

Таблица не накапливает историю по дням. Она должна всегда отражать текущее состояние источника.

### Источник

- Google Sheets: `Годовой план закупа 2026`
- Лист: `Поквартально`

### Какие поля берем

- `wild`
- `предмет`
- `3 квартал, шт 2026`

### Как обрабатываем поле `3 квартал, шт 2026`

- если значение не пустое, оно делится на `3`;
- результат округляется до `2` знаков после запятой;
- если значение пустое, в БД записывается `NULL`.

Это поле хранится как среднемесячное значение для 3 квартала 2026.

### Куда сохраняем

Таблица в PostgreSQL:

- `sales_plan_accounting_category_reference`

### Какие поля хранятся в БД

- `wild` — ключ товара
- `subject_name` — учетная категория
- `quarter_3_units_2026` — среднемесячное значение из поля `3 квартал, шт 2026`
- `created_at` — дата и время первого появления `wild` в справочнике

### Бизнес-правила

- один `wild` может быть связан только с одним `subject_name`;
- если в источнике один и тот же `wild` найден в нескольких категориях, загрузка прерывается с ошибкой;
- таблица не хранит историю по дням;
- при повторной загрузке существующий `created_at` сохраняется;
- если `wild` исчезает из источника, он удаляется из таблицы.

### Задача для запуска

- `sync_sales_plan_accounting_category_reference_to_db`

## 3. Дневной слой статусов wild

### Зачем нужен

Этот слой нужен для будущего правила расчета плана:

- если товар по итогам месяца был в наличии меньше `15` дней, план по товару обнуляется.

Так как август 2026 года уже не получится корректно посчитать ретроспективно, накопление запущено для дальнейшего расчета плана на сентябрь 2026 года и следующие месяцы.

### Источник

- Google Sheets: `Годовой план закупа 2026`
- Лист: `Поквартально`

### Какие поля берем

- `wild`
- `Статус вилд`

### Как преобразуем статус в признак наличия

На стартовом этапе зафиксировано простое правило:

- `активно` -> `is_active = true`
- любой другой статус -> `is_active = false`

Сейчас в источнике встречались, например, такие значения:

- `активно`
- `новинка`
- `закрыто`
- `вывод`

Если бизнес позже уточнит трактовку некоторых статусов, правило можно будет расширить.

### Куда сохраняем

Таблица в PostgreSQL:

- `sales_wild_status_daily`

### Какие поля хранятся в БД

- `wild` — ключ товара
- `is_active` — признак того, считался ли товар активным в этот день
- `date` — дата дневного снимка
- `created_at` — время записи snapshot в БД

### Бизнес-правила

- таблица хранит историю по дням;
- одна строка соответствует одному `wild` на одну дату;
- ключ таблицы: `date + wild`;
- если в источнике один и тот же `wild` встречается несколько раз за день, сохраняется последнее значение;
- первый боевой snapshot уже сохранен на дату `2026-08-28`.

### Задача для запуска

- `sync_sales_wild_status_daily_to_db`

## Что уже можно считать на базе этих данных

На текущем этапе уже подготовлен фундамент для следующих расчетов:

- определение менеджера по предмету на дату;
- определение единственной учетной категории для `wild`;
- накопление количества дней, когда `wild` был активен.

## Что еще не реализовано

Пока еще не сделаны следующие шаги:

1. Месячная агрегация количества активных дней по `wild`.
2. Правило обнуления плана, если активных дней в месяце меньше `15`.
3. Финальный техлист плана продаж.
4. Финальная сводная витрина плана продаж.

## Логика следующего этапа

Следующий шаг — строить месячный расчет по `wild` на базе `sales_wild_status_daily`.

Базовая логика для будущего расчета:

1. Для выбранного месяца считаем число дней, где по `wild` был `is_active = true`.
2. Если таких дней меньше `15`, план по `wild` обнуляется.
3. Если таких дней `15` и больше, план участвует в обычном расчете.
