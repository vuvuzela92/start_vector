# Почасовой мониторинг

Первый успешный финансовый срез московского часа хранится в
`autopilot_hourly_snapshots`. Повторный запуск в том же часу сохраняет этот
результат; запуск в `:30` может заполнить час, пропущенный ранним запуском.
`snapshot_at` содержит фактическое время завершения сбора необходимых источников.
Исторический `report_date` и сбор через полночь не создают новый срез.

Расчёт использует сумму и количество заказов из `wb_order_feed`, расходы Cometa
и справочники прибыли по ИУ. Границы дня заказов задаются в `Europe/Moscow`;
это может отличаться от старого `created_at::date`, если сессия PostgreSQL была
в UTC. Финансовая формула и коэффициент расходов Cometa сохранены.

## Внедрение на сервере

На время обновления остановить запуск `autopilot_hourly_run` из cron и дождаться
завершения уже работающих старых процессов: прежняя версия может перезаписывать
первый срез часа. После доставки кода выполнить из каталога проекта:

```bash
cd /root/start_vector
.venv/bin/python -m src_oop.jobs.autopilot.monitoring_snapshot migrate
.venv/bin/python -m src_oop.jobs.autopilot.monitoring_snapshot reconcile > /var/log/vector/monitoring_reconcile.json
.venv/bin/python -m src_oop.jobs.autopilot.monitoring_snapshot publish
```

Папка `/var/log/vector` должна существовать. `migrate` выполняет отдельную
повторяемую SQL-миграцию; почасовой запуск DDL не выполняет. Повтор миграции
не сбрасывает статусы доставки. `reconcile` только читает данные и формирует
JSON-отчёт с ключом, номером строки, ожидаемыми и фактическими значениями.

`publish` восстанавливает отсутствующие строки из `captured`, подтверждает
совпавшие и оставляет отличающиеся значения или дубли для разбора. Он не меняет
конфликтующие строки. Код завершения `1` означает ошибку, конфликт или занятую
блокировку; подробности находятся в журнале. После разбора можно повторить
сверку и публикацию, затем вернуть расписание hourly.

## Состояния и повторы

- `snapshot_status=captured`: достоверный срез; `unavailable`: час без точного
  среза. Старые оценочные записи `unavailable` сохраняются, новые содержат NULL
  вместо вычисленных задним числом сумм. В Sheets публикуются только `captured`.
- `delivery_status=pending`: ожидает доставки, `synced`: запись подтверждена.
  `synced_at` хранит время подтверждения, `last_delivery_error` — безопасный код
  ошибки или `sheet_conflict` / `sheet_duplicate`.
- Публикация запускается в начале hourly и после попытки сохранения нового среза.
  Архив всех дат доставляется порциями по 100 под общей advisory-блокировкой БД.
  После неопределённого результата записи повтор заново сверяет ключи A:B и
  значения C:E. Колонки технического листа остаются A:E.
- Чтение UNIT использует общий заголовок и пакет трёх колонок; при недоступности
  пропускаются остаток и скидка, остальные метрики продолжаются. Для временных
  сбоев предусмотрены четыре попытки, для 429 паузы 60/120/180 секунд с разбросом
  и учётом `Retry-After`. HTTP-запросы ограничены таймаутами подключения/чтения.

Для восстановления точного прошлого среза необходима запись `captured` в БД.
Текущие расходы и текущее состояние заказов не заменяют исторические значения.
Публикация ожидающих строк работает даже при последующем отказе источников.
Новый срез зависит от доступности списка артикулов ПУ и финансовых источников.

В сводке hourly отдельно указаны сохранение среза, доставка, конфликты,
занятость блокировки и подтверждение трёх финансовых метрик в ПУ. Ошибка
мониторинга не отменяет основной сценарий; журнал явно сообщает о пропуске.

## Проверка

```bash
python -m pytest tests/test_autopilot_monitoring.py tests/test_cometa_adv_spend.py -q
```

Интеграционные проверки создают отдельный временный PostgreSQL на localhost,
затем останавливают его. Рабочие параметры БД и настоящий Google Sheets не
используются. При необходимости каталог с `initdb` и `pg_ctl` задаётся через
`MONITORING_TEST_POSTGRES_BIN`. При отсутствии PostgreSQL интеграционные
проверки явно пропускаются, остальные тесты выполняются.
