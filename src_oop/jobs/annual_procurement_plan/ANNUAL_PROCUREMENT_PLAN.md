# Годовой план закупа

## Для чего нужен модуль

Модуль `annual_procurement_plan` собирает исходные данные для работы закупщика
в Google-таблице **«Годовой план закупа 2026»**. Он переносит текущие заказы,
остатки ФБО, фактические поставки и отзывы на парфюмерные товары, а также
обновляет цены и плановую себестоимость в листе «Поквартально».

Сам модуль не рассчитывает, сколько товара нужно заказать на год, не создает
заказы поставщикам и не формирует платежный календарь. Он обеспечивает план
данными. Формулы и ручные решения внутри Google Sheets находятся за пределами
описанной здесь Python-логики.

Документ описывает реализацию в коде, а не результаты проверки живых таблиц.
Названия таблиц, периоды SQL-выборок и правила приведены по состоянию на
29 сентября 2026 года.

## Какие данные обновляются

Все пять сценариев записывают результат в таблицу **«Годовой план закупа 2026»**.
Каждый сценарий запускается отдельной командой.

| Результат | Источник | Для чего используется | Способ записи |
| --- | --- | --- | --- |
| `БД_ЗАКАЗЫ` | «Расчет поставки Китай_по обороту»: «Заказы белые ТЕСТ» и «Заказы»; цены из PostgreSQL | Общий список заказов с ценой WB и закупочной стоимостью | Полная перезапись рабочей области |
| `Данные_Юнитки` | «UNIT 2.0 (tested)», лист «MAIN (tested)» | Суммарное значение ФБО по артикулу | Полная перезапись рабочей области |
| `Данные_Поставки` | PostgreSQL, `supply_to_sellers_warehouse` | Количество поставленного товара по дням и артикулам | Полная перезапись рабочей области |
| `Данные_Парфюм` | PostgreSQL, `wb_feedbacks` | Отзывы и оценки выбранных парфюмерных товаров | Полная перезапись рабочей области |
| `Поквартально` | Цена WB из PostgreSQL; плановая себестоимость из белых заказов | Актуализация двух ценовых ориентиров квартального плана | Запись только двух колонок |

Названия задаются в [config.py](config.py). Год в названии таблицы не меняется
автоматически с наступлением нового календарного года.

## 1. Заказы: лист «БД_ЗАКАЗЫ»

Команда: `transport_data_to_annual_procurement_plan`.

### Какие строки попадают в результат

1. Из листа «Заказы белые ТЕСТ» читаются заголовки из строки 4 и данные со строки 5.
2. Из листа «Заказы» читаются заголовки из строки 7 и данные со строки 8.
3. Выбираются нужные колонки. Отсутствующие колонки из этого набора создаются пустыми.
4. Строки белых заказов и обычных заказов объединяются друг под другом.
5. Из `Сумма заказа, RMB` удаляются поддерживаемые обозначения валют и пробелы,
   десятичная запятая заменяется точкой. Нераспознанные значения становятся пропусками.
6. Исключаются строки с перечисленными ниже статусами.
7. По артикулу добавляются цена WB и закупочная стоимость, после чего результат записывается в лист.

Исключаемые значения `Статус`:

- `отмена`;
- `в планах`;
- `прибыло`;
- `РАЗОБРАТЬСЯ`;
- `утеряно карго`;
- `не получили`;
- `излишек`;
- `недостача`.

Сравнение статусов точное: код не удаляет пробелы и не приводит их к одному
регистру. Например, `отмена` исключается, а `Отмена` или `отмена ` могут остаться.
Пустой статус сам по себе не исключает строку. Также нет отдельного условия
«количество больше нуля» или удаления повторяющихся заказов: одинаковые строки
из двух источников могут попасть в результат дважды.

### Итоговые колонки

Порядок бизнес-колонок: `wild`, `Модель`, `Статус`, `Кол-во к заказу`,
`Сумма заказа, RMB`, `нед прибытие`, `Поставщик`, `Цена WB`,
`Стоимость в закупке (руб.)`. Общий клиент выгрузки добавляет `updated_at`.

`wild` используется как артикул для сопоставления с `local_vendor_code` в БД.
При сопоставлении цен убираются пробелы по краям ключей, но регистр не меняется.
Само исходное поле `wild` при этом не переписывается.

### Откуда берется «Цена WB»

Запрос `seller_price_query` соединяет `wb_order_feed` с `article` по `nm_id`
и выбирает последнюю запись по `created_at` для каждого `local_vendor_code`.
Используется значение `seller_price` из этой записи.

Это **последняя доступная цена, а не средняя цена за неделю**. Ограничения по
давности записи нет. Цена может оказаться старой, если новых данных по товару
давно не было. Отдельного поиска последней непустой цены запрос не делает.

Если цена не найдена или равна NULL, в `БД_ЗАКАЗЫ` записывается пустая ячейка.
Цена из исходного листа заказов в этом случае не сохраняется.

### Откуда берется «Стоимость в закупке (руб.)»

Запрос `purchase_price_query` сначала выбирает допустимые записи поставок:

- `is_valid = TRUE`;
- `local_vendor_code` начинается с `wild`;
- поставщик отличается от `РВБ ООО`;
- количество не равно нулю.

Из них для каждого артикула выбирается последняя запись по
`update_document_datetime`. Это дата обновления документа, а не дата поставки.
Окна по датам нет. Условие `supplier_name != 'РВБ ООО'` в SQL также исключает
строки с NULL в имени поставщика; условие по количеству допускает отрицательные
значения, если остальные проверки пройдены.

Далее выбирается стоимость одной единицы:

| Условие | Значение для выгрузки |
| --- | --- |
| Валюта указана и отличается от кода `643`, либо имя поставщика содержит `ZILOL` без учета регистра | `planned_cost` |
| Остальные случаи | `amount_with_vat / quantity`, округленное до 2 знаков |

Пример обычной поставки: сумма с НДС 12 000 рублей, количество 30 штук.
Стоимость единицы равна 400 рублям.

Пример специального случая: при валюте, отличной от `643`, и `planned_cost = 450`
в результат попадет 450. Пересчета по валютному курсу здесь нет.

Если для специального случая `planned_cost` пустой или нулевой, SQL возвращает
диагностический `alarm_flag`, но текущая выгрузка заказов его не публикует
и не использует как причину остановки. Подстановки расчетной стоимости вместо
него нет: NULL станет пустой ячейкой, ноль останется нулем. Если подходящей
поставки вообще нет, закупочная стоимость также будет пустой.

## 2. Квартальный план: обновление цен

Команда: `update_quarterly_prices_to_annual_procurement_plan`.

Лист «Поквартально» читается с заголовками в строке 4 и данными со строки 5.
По ключу `wild` обновляются только две колонки:

| Колонка квартального плана | Источник и правило |
| --- | --- |
| `цена продажная плановая` | Последняя `seller_price` из БД, по тому же правилу, что и `Цена WB` в заказах |
| `себестоимость 2025-2026` | `Себестоимость 1 шт. в руб ПЛАН` из «Заказы белые ТЕСТ» |

Если в белых заказах артикул встречается несколько раз, для себестоимости
выбирается **последнее успешно преобразованное в число значение в порядке
строк листа**. Сортировки по дате нет. Пустые ключи и нераспознанные значения
себестоимости исключаются перед выбором. Фильтр статусов заказов из сценария
`БД_ЗАКАЗЫ` здесь не применяется.

Например, если для одного `wild` в источнике последовательно стоят `р.428,10`,
пустая ячейка и `450`, результатом будет 450. Если последние строки пустые,
будет использовано предыдущее распознанное число. Ноль считается числом и
может заменить имеющееся значение.

Если подходящей цены или себестоимости нет, сохраняется прочитанное значение
соответствующей ячейки квартального плана. Это отличает сценарий от
`БД_ЗАКАЗЫ`, где отсутствующие цены становятся пустыми.

Себестоимости двух листов нельзя считать одним показателем: в `БД_ЗАКАЗЫ`
это стоимость из последней допустимой поставки в БД, а в «Поквартально»
это плановая себестоимость из Google Sheets.

При записи есть следующие особенности:

- Обе целевые колонки должны существовать в строке заголовков.
- Записываются значения всех прочитанных строк этих двух колонок, начиная со строки 5.
- Остальные колонки и верхние строки листа не перезаписываются.
- Сохранение прежнего значения не означает сохранение формулы: чтение выполняется
  через `get_all_values()`, и в целевую колонку может вернуться результат формулы как значение.
- Две колонки записываются последовательно. При ошибке второй записи первая
  уже может быть обновлена; общей транзакции для них нет.
- Если строк данных нет, сценарий завершится без записи с предупреждением в логе.

## 3. Остатки ФБО: лист «Данные_Юнитки»

Команда: `transport_unit_data_to_annual_procurement_plan`.

Из «UNIT 2.0 (tested) / MAIN (tested)» читаются заголовки из первой строки,
данные со второй. Используются только `wild` и `ФБО`.

Из ФБО удаляются пробельные символы, затем значения приводятся к числам.
Пустые и некорректные значения заменяются нулями. Перед суммированием каждое
значение приводится к целому числу, поэтому дробная часть отбрасывается.
После этого строки группируются по `wild`, а ФБО суммируется.

Например, строки одного артикула с ФБО `1 200`, `300` и пустым значением
дадут итог 1500. Ключи `wild` в этом сценарии не очищаются от пробелов и
не приводятся к одному регистру. Формат итогового листа:
`wild`, `ФБО`, `updated_at`.

## 4. Фактические поставки: лист «Данные_Поставки»

Команда: `transport_supplies_data_to_annual_procurement_plan`.

SQL суммирует `quantity` по дню `supply_date` и `local_vendor_code` из таблицы
`supply_to_sellers_warehouse`. В выборку попадают только записи с `is_valid = TRUE`.

**Сейчас период фиксирован: с 15 марта по 15 апреля 2026 года включительно.**
Это не весь год и не скользящий период относительно дня запуска. Границы
находятся в `supplies_query` в `config.py`; параметров CLI для них нет.

Например, две допустимые поставки одного артикула за один день на 10 и 15 штук
дадут одну строку с количеством 25. Отдельного исключения отрицательных
количеств нет. Формат результата: `supply_date`, `local_vendor_code`,
`quantity`, `updated_at`.

## 5. Отзывы на парфюм: лист «Данные_Парфюм»

Команда: `transport_parfume_data_to_annual_procurement_plan`.

Из `wb_feedbacks` выбираются отзывы по фиксированному списку `nmid` в
`parfume_query`. Это не автоматический поиск всех товаров категории «Парфюм».
Для добавления товара нужно обновить список в конфигурации.

Выгружаются `nmid`, `date` (дата из `createddate`), `text`, `pros`,
`productvaluation` и добавленный клиентом `updated_at`. Ограничения по периоду,
фильтра по оценке, расчета среднего рейтинга и агрегации отзывов в запросе нет.

## Запуск

Команды выполняются из корня репозитория в настроенном Python-окружении проекта.
Нужны установленные зависимости основного проекта, доступ к PostgreSQL и
Google Sheets. Даже сценарии без SQL-запросов создают экземпляр
`AnnualProcurementPlan`, который инициализирует SQLAlchemy engine.

Подключение к БД использует переменные `DB_USER`, `DB_PASSWORD`, `DB_HOST`,
`DB_PORT`, `DB_NAME`. Общий клиент Google Sheets по умолчанию читает
`creds/creds.json` относительно корня проекта. Сервисному аккаунту нужен доступ
на чтение источников и редактирование целевой таблицы. Секреты не следует
добавлять в документацию или коммитить.

Для PowerShell с окружением `venv`:

```powershell
cd C:\Users\123\Desktop\start_vector
.\venv\Scripts\Activate.ps1
```

Выберите нужный сценарий:

```bash
python main.py transport_data_to_annual_procurement_plan
python main.py update_quarterly_prices_to_annual_procurement_plan
python main.py transport_unit_data_to_annual_procurement_plan
python main.py transport_supplies_data_to_annual_procurement_plan
python main.py transport_parfume_data_to_annual_procurement_plan
```

Это пять независимых команд, а не обязательная последовательность. Например,
обновление «Поквартально» само читает источники и не требует предварительно
обновить `БД_ЗАКАЗЫ`. Единой команды «обновить все» в модуле нет.

**Запуск сразу пишет в рабочую таблицу. Режим предварительного просмотра без
записи этими командами не предусмотрен.**

Для четырех полностью обновляемых листов общий клиент добавляет время запуска
выгрузки `updated_at`, записывает заголовки с A1 и очищает старые лишние строки
и колонки в прежней занятой области. Ручные данные и формулы в этой области
могут быть затерты. Пустая выборка не сохраняет прежний результат. Время
`updated_at` берется из локального времени процесса; это не дата исходной цены
или поставки. Для точечного обновления «Поквартально» `updated_at` не добавляется.

## Проверка результата и диагностика

| Что проверить или что пошло не так | Объяснение и действия |
| --- | --- |
| Количество строк `БД_ЗАКАЗЫ` отличается от источников | Сверить оба источника и точный список исключаемых статусов; группировки или удаления дублей заказов нет |
| Цена WB кажется устаревшей | Проверить последнюю запись `wb_order_feed.created_at` по артикулу; выборка не ограничена неделей |
| Нет закупочной стоимости | Проверить допустимость поставки и совпадение `wild` с `local_vendor_code`; для валютных поставок и ZILOL проверить `planned_cost` |
| Себестоимость «Поквартально» отличается от `БД_ЗАКАЗЫ` | Источники и правила выбора разные: план из белых заказов и стоимость из БД соответственно |
| Ручное значение «Поквартально» осталось прежним | Такое поведение ожидаемо при отсутствии цены или распознанной плановой себестоимости |
| Поставки за другие месяцы не появились | Проверить фиксированные даты в `supplies_query` |
| `KeyError` или ошибка построения DataFrame | Проверить точные названия колонок и строки заголовков; заголовки в этом модуле не нормализуются |
| Не найдена колонка при обновлении квартального плана | В строке 4 должны быть `цена продажная плановая` и `себестоимость 2025-2026` |
| `SpreadsheetNotFound` / `WorksheetNotFound` | Проверить конфигурацию названий и доступ сервисного аккаунта; в этом модуле таблицы открываются по имени |
| Ошибка авторизации Google | Проверить действительность сервисного аккаунта и используемого файла учетных данных |
| Ошибка PostgreSQL или отсутствует Python-пакет | Проверить окружение основного проекта, параметры подключения и доступ к БД |
| Временная ошибка Google Sheets | Общий клиент повторяет подключение и запись; чтение квартального плана использует retry, остальные три чтения листов вызывают `get_all_values()` напрямую |

После обновления полезно выборочно сверить один артикул с каждым источником,
проверить сохранение ручной цены при отсутствии данных и убедиться, что
в «Поквартально» изменились только нужные колонки. Совпадение общей суммы
само по себе не подтверждает правильность сопоставления по артикулам.

## Где находится логика

| Файл | Ответственность |
| --- | --- |
| [config.py](config.py) | Названия таблиц и листов; SQL для цен, поставок и отзывов |
| [annual_procurement_plan.py](annual_procurement_plan.py) | `AnnualProcurementPlan`: подключения, чтение источников, набор колонок и исключаемых статусов |
| [run.py](run.py) | Пять сценариев запуска; объединение заказов, сопоставление цен, подготовка и запись результата |
| [tasks_registry.py](../../tasks_registry.py) | Регистрация CLI-команд в разделе годового и квартального планирования |
| [my_gspread.py](../../core/my_gspread.py) | Авторизация, повторы запросов и правила записи Google Sheets |
| [database.py](../../core/database.py) | Подключение к PostgreSQL и выполнение SQL |
| [utils_general.py](../../core/utils_general.py) | Очистка денежных значений через `clean_currency_value` |

Числовая очистка удаляет поддерживаемые обозначения валют, но не конвертирует
суммы по курсу. Произвольные текстовые записи могут стать пустыми значениями.

При расширении модуля нужно учитывать общую переменную `_conn_to`: подключения
к нескольким выходным листам используют один кеш. Текущие команды создают
новый экземпляр сервиса и выбирают один такой лист. Переиспользование одного
экземпляра для последовательной записи в разные листы потребует отдельной
проверки маршрутизации. У «Поквартально» собственное подключение `_conn_quarter`.

При равных датах нескольких записей цены SQL не задает дополнительный критерий
выбора. Также источники читаются последовательно, поэтому данные из Sheets и БД
не являются единым транзакционным снимком.

Лист «Поквартально» используется и смежными сценариями проекта. Перенос плана
в свод по поставщикам описан отдельно в
[QUARTERLY_PLAN_TRANSFER.md](../calculation_of_purchases_china/QUARTERLY_PLAN_TRANSFER.md).
Расчет платежного календаря white + ВЭД относится к другому модулю и не
запускается перечисленными здесь командами.
