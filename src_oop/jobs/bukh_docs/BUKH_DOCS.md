# Бухгалтерские документы WB

Модуль `src_oop.jobs.bukh_docs` отвечает за полный контур работы с бухгалтерскими документами Wildberries:

- скачивает первичные документы WB по кабинетам;
- разбирает еженедельные отчеты реализации и уведомления о выкупе;
- сохраняет распознанные строки в PostgreSQL;
- собирает итоговую бухгалтерскую витрину `week_n_redeem`;
- выгружает витрину в Google Sheets `ОТЧЕТ за 2026 пров v.2.0`, лист `БД`.

Главная бизнес-задача модуля - подготовить понятную базу для бухгалтерии: сопоставить данные еженедельного отчета реализации, финансового отчета WB и уведомления о выкупе, чтобы видеть суммы реализации, удержаний, возвратов, выкупов и итог к перечислению по каждому кабинету и отчетному периоду.

## Сценарии запуска

### `get_bukh_docs` / `get_bukh_docs_async`

Команда:

```bash
python main.py get_bukh_docs
```

или CLI-алиас:

```bash
python main.py get_bukh_docs_async
```

Сценарий получает документы из WB Documents API и сохраняет их в PostgreSQL.

Что делает бизнес-сценарий:

- берет рабочие WB-токены по аккаунтам через `load_api_tokens`;
- запрашивает в WB список документов двух категорий: `weekly-implementation-report` и `redeem-notification`;
- скачивает найденные документы единым архивом по каждому аккаунту;
- распаковывает архивы, включая вложенные zip-файлы;
- парсит PDF еженедельных отчетов реализации;
- парсит Excel-уведомления о выкупе;
- сохраняет результат в таблицы `weekly_implementation_report` и `redeem_notification`;
- пишет в лог итог по аккаунтам: где были документы, где документов не было, где обработка упала.

По умолчанию период берется за последние 28 дней до вчерашнего дня. Если отчетный документ сформирован WB позже конца бизнес-периода, список документов запрашивается с дополнительным лагом вперед. Это важно для недельных отчетов: например, отчет за период `2026-06-15..2026-06-21` может быть сформирован только `2026-06-24`, и без лага его нельзя будет найти во вкладке документов WB.

### `update_week_n_redeem`

Команда:

```bash
python main.py update_week_n_redeem
```

Сценарий строит итоговую витрину для бухгалтерии и записывает ее в Google Sheets.

Что делает бизнес-сценарий:

- читает данные из PostgreSQL запросом `WEEK_N_REDEEM_QUERY`;
- агрегирует строки еженедельного отчета реализации;
- присоединяет финансовые отчеты WB из `fin_reports_full`;
- присоединяет уведомления о выкупе из `redeem_notification`;
- рассчитывает итоговые расходы и сумму к перечислению;
- исключает период `Конец_периода = 2025-12-31` по бизнес-логике;
- добавляет колонку `updated_at` с датой и временем обновления;
- сортирует финальные строки по `Конец_периода` по возрастанию;
- выгружает результат в таблицу `ОТЧЕТ за 2026 пров v.2.0`, лист `БД`.

Если запись в Google Sheets не удалась, задача должна завершиться ошибкой. Это защищает от ложного статуса "успешно", когда данные посчитались, но в лист `БД` не попали.

## Бизнес-логика документов

### Еженедельный отчет реализации

Источник в WB: категория `weekly-implementation-report`.

В модуле эти документы становятся таблицей `weekly_implementation_report`.

Основные поля:

- `account` - кабинет WB;
- `doc_num` - номер еженедельного отчета;
- `date` - дата отчета, которая используется как `Конец_периода` в витрине;
- `title` - строка отчета, например реализация, компенсации, штрафы, удержания;
- `sum_rub` - сумма строки отчета;
- `vat_rub` - НДС по строке.

Парсер берет только PDF-файлы вида `Отчет №...pdf`. Служебные PDF из вложенных `mchd.zip`, например `ON_EMCHD...pdf`, не являются отчетом реализации и пропускаются. Это важно: такие файлы имеют другую структуру таблиц и могут ломать объединение данных.

### Уведомление о выкупе

Источник в WB: категория `redeem-notification`.

В модуле эти документы становятся таблицей `redeem_notification`.

Основные поля:

- `account` - кабинет WB;
- `doc_name` - название документа, из которого извлекается номер уведомления;
- `wild` - артикул в формате `wild...`;
- `quantity` - количество;
- `sum_rub_with_vat` - сумма выкупа с НДС;
- `vat_rate` и `vat_sum_rub` - ставка и сумма НДС;
- `kiz` - маркировка, если присутствует.

### Финансовый отчет WB

Источник для витрины `week_n_redeem`: таблица `fin_reports_full`.

В `update_week_n_redeem` используются только строки `report_type = 2`. Они нужны, чтобы связать еженедельный отчет реализации с финансовым отчетом и уведомлением о выкупе.

## Итоговая витрина `week_n_redeem`

Витрина собирается в `week_n_redeem_queries.py` и дополнительно обрабатывается в `week_n_redeem_service.py`.

Ключевые правила:

- недельный отчет связывается с фин. отчетом по аккаунту и дате окончания периода;
- уведомление о выкупе связывается через номер реализации `realizationreport_id`;
- НДС пересчитывается через справочник `vat_guide`;
- период с `Конец_периода = 2025-12-31` исключается;
- итоговая сортировка перед Google Sheets идет по `Конец_периода`, затем по `account`, затем по `Номер_еженедельного_отчета`;
- `updated_at` добавляется последней колонкой и показывает время подготовки текущей выгрузки.

Расчетные поля:

- `Итого_расходы` - сумма удержаний и расходов с учетом знака вознаграждения WB;
- `К_перечислению_по_отчетам` - итог к перечислению по отчетам с учетом реализации, компенсаций, выплат, уведомления о выкупе и расходов.

## Расчет метрик для таблицы «ОТЧЕТ за 2026 пров v.2.0»

Лист `БД` является расчетной витриной, а не копией одного документа WB. Одна
строка соответствует сочетанию `account + Номер_еженедельного_отчета +
Конец_периода`. Сначала строки исходных документов агрегируются, затем данные
объединяются в одну бухгалтерскую строку.

### Определение периода

- `Начало_периода` — начало календарной недели, рассчитанное через
  `DATE_TRUNC('week', weekly_implementation_report.date)`.
- `Конец_периода` — дата отчета реализации (`date`), по которой выполняется
  сопоставление с `fin_reports_full.date_to`. Это не обязательно дата
  формирования документа в личном кабинете WB.
- Отчеты с датой не позднее `2025-01-31` исключаются SQL-запросом. Период с
  `Конец_периода = 2025-12-31` дополнительно исключается перед записью в `БД`
  по бизнес-правилу.

### Источники данных и связи

Для расчета используются три источника:

1. `weekly_implementation_report` — реализация, компенсации, выплаты,
   вознаграждение и удержания из еженедельного отчета реализации.
2. `fin_reports_full` — возврат выкупа (`ppvz_for_pay`) из финансового отчета
   WB с `report_type = 2`. Связь выполняется по кабинету и дате окончания
   периода.
3. `redeem_notification` — сумма выкупленного товара. Связь выполняется по
   `fin_reports_full.realizationreport_id`, номеру уведомления, извлеченному из
   `doc_name`, и кабинету.

Если финансовый отчет или уведомление о выкупе не найдены, соответствующая
сумма подставляется как `0`, а строка реализации сохраняется. Так бухгалтерия
видит сам факт отчета, а неполное сопоставление диагностируется по логам
`missing_redeem_notifications`.

### Реализация, компенсации и выкуп

- `Всего_стоимость_реализованного_товара` — сумма строк с названием `Итого
  стоимость реализованного товара и услуг`.
- `Всего_стоимость_реализованного_товара_без_НДС` — та же сумма без НДС:
  `sum_rub / (1 + vat)`, округление до 2 знаков.
- `Компенсации_ущерба` — сумма строк `Компенсация ущерба`.
- `Прочие_выплаты` — сумма строк `Прочие выплаты`.
- `Компенсация_скидки_по_программе_лояльности` — сумма строк с одноименным
  названием WB.
- `Выкуплено_по_уведомлению` — сумма `redeem_notification.sum_rub_with_vat`.
- `Выкуплено_по_уведомлению_без_НДС` — сумма выкупа без НДС по формуле
  `sum_rub_with_vat / (1 + vat)`, округление до 2 знаков.
- `Вовзрат_выкупа` — сумма `fin_reports_full.ppvz_for_pay` по строкам, где
  `doc_type_name` содержит `возврат`.

Ставка `vat` берется из справочника `vat_guide` по кабинету. При сопоставлении
имя кабинета очищается от пробелов и приводится к верхнему регистру. Отсутствующие
суммы заменяются на `0` через `COALESCE`, чтобы пропуск отдельной категории не
удалял всю строку отчета. Если ставка отсутствует в `vat_guide`, показатель без
НДС будет пустым, поэтому для каждого рабочего кабинета должна быть явная строка
в справочнике.

Для кабинетов групп `СТАРТ*` и `ВЕКТОР*` используется ставка НДС `22%`, то
есть `vat = 0.22`. Недостающие записи добавляются в PostgreSQL идемпотентно:

```sql
UPDATE vat_guide
SET vat = 0.22
WHERE UPPER(TRIM(account)) = 'СТАРТ3925';

INSERT INTO vat_guide (account, vat)
SELECT 'СТАРТ3925', 0.22
WHERE NOT EXISTS (
    SELECT 1
    FROM vat_guide
    WHERE UPPER(TRIM(account)) = 'СТАРТ3925'
);
```

Перед массовым добавлением нужно заменить пример на полный список рабочих
кабинетов. Это сохраняет явный и проверяемый справочник ставок и не применяет
ставку автоматически к неизвестному кабинету только из-за похожего имени.

### Вознаграждение и удержания

`Вознаграждение` — сумма строк `Сумма вознаграждения Вайлдберриз за текущий
период (ВВ), без НДС` и `НДС с вознаграждения Вайлдберриз`.

Отдельно собираются следующие расходы и удержания:

- `Сумма_удержанная_в_счёт_обеспечения_организации_платежа`;
- `Возмещение расходов по перевозке` или новое название WB
  `Возмещение издержек по перемещению и операционной обработке товара`;
- `Возмещение_за_выдачу_и_возврат_товаров_на_ПВЗ`;
- `Штрафы`;
- `Прочие удержания`;
- `Удержания_в_пользу_третьих_лиц`.

WB обычно передает вознаграждение отрицательным числом. Поэтому отрицательное
значение переносится в положительный показатель `Вознагрожденение_в_доход`:

```text
Вознагрожденение_в_доход = -Вознаграждение, если Вознаграждение < 0
Вознагрожденение_в_доход = 0, если Вознаграждение >= 0
```

`Вознагрожденение_в_доход_БЕЗ_НДС` рассчитывается аналогично, но дополнительно
делится на `1 + vat` и округляется до 2 знаков.

### Итоговые формулы

Если `Вознаграждение < 0`:

```text
Итого_расходы = Вовзрат_выкупа
              + Возмещение расходов по перевозке
              + Возмещение_за_выдачу_и_возврат_товаров_на_ПВЗ
              + Штрафы
              + Прочие удержания
              + Удержания_в_пользу_третьих_лиц
              + Сумма_удержанная_в_счёт_обеспечения_организации_платежа
```

Если `Вознаграждение >= 0`, к этой сумме добавляется исходное
`Вознаграждение`.

```text
К_перечислению_по_отчетам = Всего_стоимость_реализованного_товара
                          + Компенсации_ущерба
                          + Прочие_выплаты
                          + Выкуплено_по_уведомлению
                          + Вознагрожденение_в_доход
                          - Итого_расходы
```

Таким образом, отрицательное вознаграждение увеличивает сумму к перечислению
через показатель дохода и не входит в расходы. Положительное вознаграждение
увеличивает `Итого_расходы` и уменьшает итог к перечислению.

Оба названия статьи WB считаются одной бизнес-категорией. Их сумма сохраняется
в прежней колонке `Возмещение расходов по перевозке`, поэтому структура листа
`БД` и формулы пользователей таблицы не меняются. Если в одном отчете временно
присутствуют обе формулировки, суммы обеих строк складываются.

### Подготовка перед записью в Google Sheets

Перед записью в лист `БД` сервис нормализует имена колонок, добавляет
`updated_at` последней колонкой, исключает `2025-12-31`, а затем сортирует
строки по `Конец_периода` по возрастанию, затем по `account` и
`Номер_еженедельного_отчета`. Сортировка не меняет суммы, а обеспечивает
хронологичный порядок просмотра данных бухгалтерией.

Если в логах есть `missing_redeem_notifications`, это означает, что для части строк витрины не нашлось связанного уведомления о выкупе. Это не всегда техническая ошибка: нужно смотреть бизнес-период, наличие документа WB и связь с `fin_reports_full`.

## Настройки

Основные настройки находятся в `config.py`.

| Настройка | Значение по умолчанию | Бизнес-смысл |
| --- | --- | --- |
| `DEFAULT_DAYS_BACK` | `28` | Сколько дней назад брать при запуске без явного периода. |
| `DEFAULT_DATE_TO_OFFSET` | `1 день` | Верхняя граница периода по умолчанию - вчера. |
| `WB_DOCS_LIST_DATE_TO_LAG_DAYS` | `7` | Насколько расширять поиск документов вперед по дате формирования WB. |
| `WB_DOCS_FILTER_WEEKLY_BY_REPORT_DATE` | `False` | Фильтровать ли строки weekly report строго по внутренней дате отчета. |
| `MAX_CONCURRENCY` | `3` | Сколько аккаунтов обрабатывать параллельно. |
| `RETRY_ATTEMPTS` | `5` | Количество повторов запросов к WB API. |

### `WB_DOCS_FILTER_WEEKLY_BY_REPORT_DATE`

По умолчанию выключен.

Причина: документ за нужный бизнес-период может быть сформирован WB позже. Если жестко фильтровать по дате формирования документа, можно потерять отчет, который относится к нужной неделе, но появился в ЛК позже.

Включать фильтр стоит только для точечной диагностики, когда нужно проверить, какие строки weekly report попадают строго в заданный период.

Пример для Windows cmd:

```cmd
set WB_DOCS_FILTER_WEEKLY_BY_REPORT_DATE=True
python main.py get_bukh_docs
```

## Таблицы PostgreSQL

### `weekly_implementation_report`

Уникальный ключ:

```text
doc_num, №, account
```

Назначение: хранит строки еженедельных отчетов реализации WB.

### `redeem_notification`

Уникальный ключ:

```text
doc_name, №, account
```

Назначение: хранит строки уведомлений о выкупе WB.

Уникальные ключи нужны, чтобы повторный запуск не создавал дубли при повторной загрузке уже скачанных документов.

## Google Sheets

Итоговая выгрузка пишется в:

```text
Таблица: ОТЧЕТ за 2026 пров v.2.0
Лист: БД
```

Запись выполняется через `set_with_dataframe`, то есть лист перезаписывается содержимым итогового DataFrame.

При временных проблемах Google Sheets модуль повторяет запись несколько раз. Повторяются только временные ошибки:

- DNS/connection error;
- timeout;
- HTTP 429;
- HTTP 500, 502, 503, 504.

Ошибки прав доступа, неверного листа или структуры таблицы не ретраятся, потому что требуют ручного исправления.

## Логи и диагностика

Ключевые строки для `get_bukh_docs`:

```text
Старт bukh_docs job
Старт обработки аккаунта bukh_docs
Собран список документов WB
Документы WB скачаны
Архив документов распакован
PDF weekly report распознан
Redeem Excel распознан
Завершена обработка аккаунта bukh_docs
Завершен bukh_docs job
Итог по аккаунтам bukh_docs
```

Ключевые строки для `update_week_n_redeem`:

```text
Старт week_n_redeem job
Получен DataFrame week_n_redeem
week_n_redeem snapshot: stage=sql_result
week_n_redeem snapshot: stage=processed_result
Фильтр Конец_периода != 2025-12-31
Финальная сортировка week_n_redeem перед записью в Google Sheets выполнена
week_n_redeem snapshot: stage=filtered_result
Данные week_n_redeem записаны в Google Sheets
Завершен week_n_redeem job
```

Если в конце `get_bukh_docs` есть `status=failed`, значит ни по одному аккаунту не удалось записать данные. Если `status=partial`, часть данных записалась, но были ошибки по отдельным аккаунтам или таблицам.

Если `update_week_n_redeem` завершился ошибкой после `filtered_result`, значит данные подготовлены, но не попали в Google Sheets. Чаще всего причина в доступе к Google API, сети, DNS или правах сервисного аккаунта.

## Частые проблемы

### В лист `БД` не попали данные, хотя SQL собрал строки

Проверить логи после строки:

```text
week_n_redeem snapshot: stage=filtered_result
```

Если дальше ошибка вида:

```text
Failed to resolve 'sheets.googleapis.com'
```

то проблема в сети/DNS до Google Sheets API, а не в данных.

### Скачались документы, но не все аккаунты попали в итоговую витрину

Проверить:

- есть ли weekly report за нужный период в `weekly_implementation_report`;
- есть ли связанный `fin_reports_full` с `report_type = 2`;
- совпадает ли `realizationreport_id` с номером уведомления о выкупе;
- есть ли строки в `redeem_notification`;
- не попал ли период под бизнес-исключение `2025-12-31`.

### WB показывает отчет в ЛК, но модуль его не нашел

Проверить дату формирования документа в WB. Если документ за бизнес-период сформирован позже, должен помочь лаг `WB_DOCS_LIST_DATE_TO_LAG_DAYS`. По умолчанию он равен 7 дням.

### Ошибка `Reindexing only valid with uniquely valued Index objects`

Исторически такая ошибка возникала, когда парсер принимал служебные PDF МЧД за weekly report. Сейчас PDF из `mchd.zip` и файлы `ON_EMCHD...pdf` пропускаются как служебные.

## Безопасность

В логах нельзя выводить токены WB, cookies, ключи Google, DSN и другие секреты. Модуль логирует аккаунт, категорию документа, статус запроса, количество строк и безопасные диагностические признаки.

При доработке модуля важно сохранять это правило: любые заголовки HTTP, токены и credentials не должны попадать в лог и текст исключений.

## Рекомендованный порядок проверки после изменений

1. Проверить синтаксис:

```bash
python -m compileall src_oop/jobs/bukh_docs
```

2. Запустить загрузку документов:

```bash
python main.py get_bukh_docs
```

3. Проверить лог `Завершен bukh_docs job`.

4. Запустить обновление витрины:

```bash
python main.py update_week_n_redeem
```

5. Проверить, что в логах есть:

```text
Данные week_n_redeem записаны в Google Sheets
```

6. Открыть лист `БД` и проверить:

- строки есть;
- `Конец_периода` отсортирован по возрастанию;
- колонка `updated_at` находится в конце;
- ожидаемые аккаунты присутствуют в нужном периоде.
