# LOGISTIC_VED

## Назначение модуля

Модуль `src_oop/jobs/logistic_ved` обслуживает рабочий процесс между закупщиками и логистами по белым заказам из Китая.

В процессе участвуют две основные Google Таблицы:

- источник закупщиков: `Расчет поставки Китай_по обороту` -> лист `Заказы белые ТЕСТ`
- рабочая таблица логистов: `Логистика ВЭД 2026` -> лист `ОТЧЁТ_2.0`

Ключ сопоставления между таблицами:

- `ORDER_LINE_ID`

Главная боевая задача модуля:

- `logistic_ved_full_run`

Именно она должна использоваться для регулярного запуска. Отдельные прямой и обратный сценарии в реестре задач не публикуются, чтобы не создавать путаницу в эксплуатации.

---

## Бизнес-логика процесса простым языком

Процесс разделен на две роли.

### 1. Закупщики

Закупщики ведут первичную информацию по заказу в таблице `Заказы белые ТЕСТ`:

- `wild`
- `Модель`
- `Номер Трака`
- `КОМПАНИЯ`
- `Фабрика`
- `Поставщик`
- `Статус`
- `Кол-во к заказу`
- `Кол-во коробок`
- `объем партии, м3`
- `вес партии, кг`
- `Сумма заказа, RMB`
- `ORDER_LINE_ID`

Но в работу логистов передаются не все строки, а только те, которые действительно готовы к следующему этапу.

### 2. Логисты

После того как строка попала в `ОТЧЁТ_2.0`, логисты начинают вести ее дальше уже как свою операционную запись:

- добавляют логистические даты и номера
- меняют статус по своей бизнес-логике
- работают независимо от закупщиков

Ключевое правило:

- если строка уже существует в `ОТЧЁТ_2.0`, то поле `Статус` больше не должно перезаписываться обратно из таблицы закупщиков

Это сделано специально, чтобы не возникал цикл:

- логисты выставили свой статус
- обратная синхронизация вернула закупщикам согласованный статус
- прямая синхронизация снова затерла логистический статус значением закупщиков

---

## Точка входа

Боевая точка входа находится в:

- `src_oop/jobs/logistic_ved/run.py`

Функция:

- `logistic_ved_full_run()`

Порядок работы:

1. сначала запускается `logistic_ved_reverse_run`
2. затем запускается `logistic_ved_run`

Это означает:

1. сначала закупщики получают обратно изменения от логистов
2. затем в `ОТЧЁТ_2.0` подтягиваются новые или обновленные строки из таблицы закупщиков

## Структура модуля

### `config.py`

### `__init__.py`

Экспортирует только боевую точку входа:

- `logistic_ved_full_run`

### `LOGISTIC_VED.md`

Этот документ. Нужен как единое описание технической и бизнес-логики модуля.

## Прямая синхронизация: `logistic_ved_run`

### Что делает

`logistic_ved_run` читает данные закупщиков из `Заказы белые ТЕСТ` и переносит их в `ОТЧЁТ_2.0`.

### Какие строки попадают в работу логистов

Строка попадает в `ОТЧЁТ_2.0`, только если одновременно выполняются условия:

- `Номер Трака` не пустой
- `Статус = товар готов к вывозу`
- `ORDER_LINE_ID` не пустой

### Какие поля переносятся

Состав управляемых полей задается в `CHINA_COLS`.

На текущий момент это:

- `wild`
- `Модель`
- `Номер Трака`
- `КОМПАНИЯ`
- `Фабрика`
- `Поставщик`
- `Статус`
- `Кол-во к заказу`
- `Кол-во коробок`
- `объем партии, м3`
- `вес партии, кг`
- `Сумма заказа, RMB`
- `ORDER_LINE_ID`

### Как происходит обновление

Сопоставление выполняется строго по `ORDER_LINE_ID`.

Если `ORDER_LINE_ID` уже есть в `ОТЧЁТ_2.0`:

- обновляются только управляемые поля закупщиков
- поле `Статус` не обновляется
- поле `updatet_at` обновляется текущим временем
- остальные поля логистов сохраняются как есть

Если `ORDER_LINE_ID` в `ОТЧЁТ_2.0` еще нет:

- строка добавляется как новая
- в `created_at` записывается дата и время первого появления
- в `updatet_at` записывается дата и время текущего обновления
- стартовый статус переносится из таблицы закупщиков

### Важные технические правила

- заголовки в `ОТЧЁТ_2.0` находятся в 4-й строке
- данные в `ОТЧЁТ_2.0` начинаются с 5-й строки
- скрипт не перезаписывает весь лист целиком
- скрипт делает только точечные изменения по ячейкам и добавляет новые строки
- ячейка `A2` в `ОТЧЁТ_2.0` хранит дату и время последнего успешного обновления прямой синхронизации

### Особенности обработки суммы

Поле `Сумма заказа, RMB` при чтении нормализуется:

- удаляется валютный символ
- убираются пробелы и неразрывные пробелы
- значение приводится к числу, если это возможно

Это нужно, чтобы сумма в `ОТЧЁТ_2.0` была числом, а не строкой вида `¥169 164,00`.

## Обратная синхронизация: `logistic_ved_reverse_run`

### Что делает

`logistic_ved_reverse_run` возвращает из `ОТЧЁТ_2.0` обратно в `Заказы белые ТЕСТ` только ту информацию, которой уже управляют логисты.

### Какие поля возвращаются закупщикам

Список задается в `LOGISTIC_TO_CHINA_SYNC_COLS`.

На текущий момент это:

- `ФАКТИЧЕСКАЯ ДАТА ОТГРУЗКИ ОТ НАС`
- `Номер ТС`
- `План прибытия на склад`
- `ФАКТИЧЕСКАЯ ДАТА ПРИБЫТИЯ НА СКЛАД ОТ НАС`

### Как выполняется сопоставление

Сопоставление также идет строго по `ORDER_LINE_ID`.

Если строка есть в `ОТЧЁТ_2.0`, но отсутствует в `Заказы белые ТЕСТ`, обратная запись по ней не выполняется.

### Как синхронизируются статусы

Статусы между таблицами не обязаны совпадать дословно.

Поэтому действует таблица соответствий:

- `принят складом` -> в таблицу закупщиков записывается `прибыло`
- `растаможен, в пути на склад` -> `в пути`
- `в пути` -> `в пути`
- `Таможня` -> `в пути`
- `Таможня ЗБК` -> `в пути`
- `осмотр/ досмотр/ проблема` -> `в пути`

Статус `Ждём загрузку` в `ОТЧЁТ_2.0` считается корректным при статусе `товар готов к вывозу` у закупщиков и не считается ошибкой сверки.

### Сверка данных между таблицами

Во время обратной синхронизации модуль сверяет между собой:

- `wild`
- `Кол-во к заказу`
- `Статус`

В поле `Сверка данных` может ставиться:

- `Сверьте wild и количество`
- `Сверьте wild, количество и статус`

Если расхождение исчезло, модуль сам очищает только те сообщения, которые ранее поставил он сам автоматически.

### Важные технические правила

- заголовки в `Заказы белые ТЕСТ` находятся в 4-й строке
- данные в `Заказы белые ТЕСТ` начинаются с 5-й строки
- обновления в обе таблицы выполняются пакетно через `batch_update`
- ячейка `B1` в `Заказы белые ТЕСТ` хранит дату и время последней успешной обратной синхронизации

## Автозаполнение даты прибытия на склад из БД

### Что заполняется

Поле:

- `ФАКТИЧЕСКАЯ ДАТА ПРИБЫТИЯ НА СКЛАД ОТ НАС`

в таблице:

- `ОТЧЁТ_2.0`

### Источник данных

Источник:

- PostgreSQL
- таблица `supply_to_sellers_warehouse`

Используется SQL-запрос `TRUCK_ARRIVAL_DATE_QUERY`.

### Правило сопоставления

Сопоставление выполняется:

- по `Номер Трака` из `ОТЧЁТ_2.0`
- с `truck_number` из БД

### Правила обновления

Если по траку в БД найдена ровно одна дата:

- поле обновляется этой датой

Если по траку в БД ничего не найдено:

- ячейка не перезаписывается

Если по одному траку найдено несколько разных дат:

- ячейка не перезаписывается
- в лог пишется предупреждение

### Формат даты

Дата записывается в формате:

- `ДД.ММ.ГГГГ`

## Финальная автопроверка приемки из БД

### Что делает

После основной обратной синхронизации модуль отдельно проходит по всем строкам `ОТЧЁТ_2.0` и пытается автоматически определить итоговый статус приемки.

Этот шаг относится именно к рабочей таблице логистов и выполняется в конце `logistic_ved_reverse_run`.

### Источник данных

Источник:

- PostgreSQL
- таблица `supply_to_sellers_warehouse`

Используется SQL-запрос `SUPPLY_ACCEPTANCE_STATUS_QUERY`.

### Ключ сопоставления

Для автопроверки используется полное совпадение по четырем полям:

- `Номер Трака`
- `Номер ТС`
- `wild`
- `Номер заказа в 1С`

После совпадения этого ключа отдельно сверяется количество:

- `Кол-во к заказу` из `ОТЧЁТ_2.0`
- `quantity` из БД

### Правила смены статуса

Если совпали:

- `Номер Трака`
- `Номер ТС`
- `wild`
- `Номер заказа в 1С`
- количество

то в `ОТЧЁТ_2.0` ставится:

- `принят складом`

Если совпали:

- `Номер Трака`
- `Номер ТС`
- `wild`
- `Номер заказа в 1С`

но количество не совпало, то в `ОТЧЁТ_2.0` ставится:

- `расхождения при приемке`

Если не совпал хотя бы один элемент ключа:

- статус автоматически не меняется

Если по одному ключу в БД найдено несколько строк:

- статус автоматически не меняется
- в лог пишется предупреждение

## Почему используется `spreadsheet_id`

Для таблицы `Расчет поставки Китай_по обороту` зафиксирован:

- `spreadsheet_id = 1fXiijP8vMYv8vEFN1BnnTcqioCT_P2t1tgogi_ATh_8`

Это защита от ситуации, когда кто-то вручную переименовал Google Таблицу.

Если `spreadsheet_id` задан:

- подключение идет по `id`
- если фактическое название изменилось, в лог пишется предупреждение
- сценарий продолжает работу с правильным документом

Это защищает `logistic_ved_full_run` от падения с ошибкой `SpreadsheetNotFound` только из-за смены названия документа.

## Что важно помнить при ручных правках

### Если нужно добавить новое поле из закупщиков в `ОТЧЁТ_2.0`

Обычно достаточно:

- добавить название колонки в `CHINA_COLS`

Но перед этим нужно проверить:

- существует ли такая колонка в `Заказы белые ТЕСТ`
- существует ли такая колонка в `ОТЧЁТ_2.0`
- должно ли поле обновляться и для уже существующих строк
- не относится ли это поле к зоне ответственности логистов

### Если нужно добавить новое поле, которое логисты возвращают закупщикам

Нужно:

- добавить колонку в `LOGISTIC_TO_CHINA_SYNC_COLS`
- убедиться, что колонка существует в обеих таблицах

### Если нужно поменять фильтр попадания строки в `ОТЧЁТ_2.0`

Смотреть:

- `CHINA_FILTER_COLS`
- логику метода подготовки источника в `run.py`

### Если нужно поменять статусные правила

Смотреть:

- `ALLOWED_SOURCE_STATUSES_BY_TARGET_STATUS`
- `TARGET_STATUS_BY_SOURCE_STATUS`

### Если нужно поменять правила автоприемки

Смотреть:

- `SUPPLY_ACCEPTANCE_STATUS_QUERY`
- финальный блок приемки в `reverse_run.py`

### Если нужно поменять логику даты прибытия на склад

Смотреть:

- `TRUCK_ARRIVAL_DATE_QUERY`
- блок автозаполнения даты по `Номер Трака` в `reverse_run.py`

## Технические гарантии модуля

Модуль специально построен так, чтобы:

- не удалять строки из `ОТЧЁТ_2.0`
- не перезаписывать весь лист целиком
- не трогать заголовки и верхние служебные строки
- не очищать ячейки, если в БД нет подтверждающих данных
- не перезаписывать логистический статус обратно статусом закупщиков
- не зависеть только от названия исходной Google Таблицы

## Типовые причины расхождений

### В `ОТЧЁТ_2.0` не меняется статус на `принят складом`

Обычно причина в одном из пунктов:

- не совпал `Номер Трака`
- не совпал `Номер ТС`
- не совпал `wild`
- не совпало количество
- по одному ключу в БД нашлось несколько строк

### Не заполнилась `ФАКТИЧЕСКАЯ ДАТА ПРИБЫТИЯ НА СКЛАД ОТ НАС`

Обычно причина в одном из пунктов:

- в `ОТЧЁТ_2.0` пустой `Номер Трака`
- по этому траку в БД нет даты
- по этому траку в БД найдено несколько разных дат

### `logistic_ved_full_run` не может открыть таблицу закупщиков

Сначала проверить:

- корректен ли `spreadsheet_id`
- существует ли лист `Заказы белые ТЕСТ`
- не удален ли доступ у сервисного аккаунта

## Актуальное состояние на 31 августа 2026 года

На текущий момент модуль работает по таким ключевым правилам:

- запускать нужно только `logistic_ved_full_run`
- `Статус` в существующих строках `ОТЧЁТ_2.0` не перезаписывается из таблицы закупщиков
- логистические поля возвращаются закупщикам из `ОТЧЁТ_2.0`
- дата прибытия на склад подставляется из БД по `Номер Трака`
- финальная автопроверка приемки работает по ключу `Номер Трака + Номер ТС + wild`
- при несовпадении количества ставится `расхождения при приемке`
- при ручном переименовании исходной Google Таблицы подключение сохраняется по `spreadsheet_id`
